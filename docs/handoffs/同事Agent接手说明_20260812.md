## 2. 项目一句话

新版智训通是一个面向客服、面试官、内训师等垂直场景的 AI 训练 SaaS，核心闭环是：

```text
行业/知识库配置 -> AI 创建训练场景 -> 发布训练任务 -> 学员 AI 对练/考试 -> AI 评分复盘 -> 申诉/统计/运营管理
```

当前阶段重点不是做静态演示，而是做真实可用的管理端 H5 + 独立 API + SQLite 持久化闭环，后续要能迁移 MySQL 和 SaaS 部署。

## 3. 技术架构

### 3.1 Monorepo 结构

| 目录 | 作用 |
|---|---|
| `apps/admin` | 管理端 H5 / 学员相关页面，Next.js 前端 |
| `apps/api` | 独立 API 服务，Next.js Route Handler |
| `packages/database` | SQLite/Prisma 数据访问、仓储、初始化脚本 |
| `packages/shared` | 前后端共享类型、接口 schema、领域类型 |
| `packages/ai-provider` | LLM/STT/TTS 等 AI 能力适配层 |
| `docs` | 设计、计划、交接、原型对齐说明 |
| `deploy` | Docker/Nginx/测试部署相关文件 |

### 3.2 核心约束

- `apps/admin` 只能通过 HTTP API 访问数据。
- `apps/api` 是唯一后端入口，负责认证、租户隔离、AI 调用、文件处理和审计。
- 不允许把模型 Key、数据库访问、文件系统访问写到前端。
- SQLite 只是本地验证，表结构和数据访问要考虑迁移 MySQL。
- LLM、STT、TTS、OCR、评分都应该是可替换接口，不要绑定死某一家供应商。

4. 优化 AI 对练体验：TTS 声音、情绪、STT 麦克风权限、对练轮次、评分复盘。
5. 补齐 SaaS 部署能力：租户隔离、套餐额度、用量统计、配置加密、生产环境禁用开发头。

## 6. 原型对齐要求

原型地址：

```text
https://tmp.artcross.xyz/prototypes/zxt-static-pages/
```

基本规则：

- 严格按原型截图逐项对齐，不脑补布局。
- 正文 14px，页面标题 24px，卡片标题 20px，统计卡数字 24px。
- 智训通当前主色以蓝系为主，避免回到旧红色系统。
- 页面要同时检查：顶部、左侧菜单、主内容、右侧卡片、按钮、空状态、弹窗、滚动区域。
- 任务详情、我的任务、对练中心要特别看排版宽度、右侧卡片占位、内容是否被截断。
- 删除确认、场景创建模式、知识库选择、考试解析等交互不要用浏览器原生 `window.confirm`。

验收建议：

1. 先看页面是否和原型一致。
2. 再点所有主按钮，确认没有“点击无反应”。
3. 再刷新页面，确认数据仍来自数据库。
4. 最后看移动端或窄屏是否明显错位。

## 7. 数据真实性要求

宏哥明确要求：不要演示假闭环，要真实数据。

开发时注意：

- 页面统计数字不得写死。
- 任务数量、进行中、已完成、逾期等必须由任务/参与记录计算。
- 培训概况、通知消息、训练记录、考试记录要有数据库来源。
- 能力模型、评分规则、任务场景、知识库摘要要能追溯。
- 前端只展示 API 返回的数据；没有数据时展示合理空状态。
- 不要用“为了好看”的静态数组长期占位，临时占位也要写 TODO 并尽快接 API。

建议新增功能时同步检查：

```text
页面组件 -> API route -> repository -> SQLite init/Prisma schema -> seed/测试数据
```

## 8. AI 对练与语音链路

对练相关重点文件：

- `apps/admin/app/practice/page.tsx`
- `apps/admin/app/practice/practice.css`
- `apps/api/app/api/ai/chat/route.ts`
- `apps/api/app/api/ai/tts/synthesize/route.ts`
- `apps/api/tts_synth.py`
- `apps/api/chattts_service.py`
- `apps/api/sherpa_tts_service.py`
- `scripts/start-chattts.mjs`
- `scripts/stop-chattts.mjs`
- `scripts/start-sherpa-tts.mjs`

已知要求：

- edge-tts 声音曾被反馈机械，TTS 要向更自然的声音演进。
- 不同场景可随机男/女声，但同一场景内声音必须固定一致。
- 情绪要明显，尤其 angry/urgent，客服训练要有真实压力。
- 学员点击说话时应停止 AI 当前语音，避免边播边录。
- 浏览器麦克风必须在 HTTPS 或 localhost 下可用；如果提示无法访问麦克风，优先查协议、权限、CSP、浏览器设置。

注意：

- 当前代码可能已经在 ChatTTS / Sherpa / 旧版服务 / edge-tts fallback 之间调整过，接手时以实际代码为准。
- 不要把 TTS 供应商调用写死在前端页面。

## 10. 部署边界

生产/测试服务器上已有老智训通和其他应用。任何部署相关动作必须谨慎：

- 新版 zxt-next 默认旁路部署，不影响既有服务。
- 不删除服务器文件、镜像、容器、数据卷、数据库。
- 不停止或重启无关服务。
- 不改 Nginx 全局配置，除非宏哥明确授权。
- 不把敏感配置提交到 Git。

已知 zxt-next 部署口径：

| 项 | 口径 |
|---|---|
| Admin 宿主端口 | 13000 |
| API 宿主端口 | 14000 |
| 服务器目录 | `/data/zxt-next` |
| Compose | `/data/zxt-next/deploy/docker-compose.test.yml` |
| 持久化 | `/data/zxt-next/storage` |
| 日志 | `/data/zxt-next/logs` |

涉及 `/zxtb/` 子路径时重点检查：

- `NEXT_PUBLIC_APP_BASE_PATH`
- Next.js `basePath`
- Nginx `/zxtb/` 页面代理
- Nginx `/zxtb/api/` -> API 代理
- `/_next/` 静态资源路径
- 页面缓存 `no-store/no-cache`
- CSP 是否允许 STT WebSocket 和音频资源

## 11. 协作开发建议

### 11.1 分支策略

- 每个人从最新 `main` 拉功能分支。
- 分支建议命名：`feature/<模块>-<姓名或缩写>`、`fix/<问题>`。
- 每次只做一个明确模块，避免大面积改多个页面。
- 提交前看 `git diff --stat`，确认没有误改无关文件。
- 不要 `git add .`，优先明确添加自己改的文件。

### 11.2 模块分工建议

可以按下面方式拆：

| 模块 | 适合处理内容 |
|---|---|
| 原型/UI 对齐 | 页面布局、CSS、弹窗、空状态、按钮跳转 |
| 数据真实性 | 静态数据清理、API、repository、SQLite seed |
| AI 对练 | STT/TTS、chat、评分、训练记录、对练体验 |
| 任务/场景 | 创建任务、发布、任务详情、场景配置、评分规则 |
| 知识库 | 上传、解析、OCR、摘要、场景生成引用 |
| SaaS/系统 | 租户、套餐、权限、配置加密、审计 |

### 11.3 代码评审重点

- 是否破坏租户隔离。
- 是否把假数据当真数据展示。
- 是否新增硬编码 URL、Key、密码。
- 是否影响 `/zxtb/` 子路径部署。
- 是否有 TypeScript 错误或构建错误。
- 是否按钮可点、接口可用、刷新后数据仍存在。
- 是否和原型主视觉一致。
